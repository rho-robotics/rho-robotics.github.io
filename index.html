RHO: Your Coding Agent is Secretly a Roboticist

  • Accepted at the Sim2Real2Field Workshop @ CoRL 2026
  • Accepted at the 2nd Workshop on Lifelong Agents @ COLM 2026

RHO (Robotics Harness Optimization) unlocks tool-enabled LLM coding agents to unleash their inner roboticist. Through reflective evolutionary search, it writes and rewrites a robot's control code in simulation until the code itself solves the task, reaching state of the art among Code-as-Policies methods.

01The bottleneck

Past research

Prior systems kept a language model in the loop to edit code during deployment

Recent CaP systems rely on iterative code generation loops at test time, often leaving them unsuitable for real-time robotics tasks.

  • 68.29% to 24% without multi-turn scaffolding

Robotics Harness Optimization

  • Shifts the compute burden from test-time to training-time
  • Ships a readable repository you can inspect
  • Same action primitives, higher success rate
02The flip

The idea

Let a coding agent write and rewrite the robot's code until it works.

RHO hands the job to a tool-enabled coding agent and lets it practice in a simulator through reflective evolutionary search: it edits, runs, and debugs whole programs against a scalar reward, keeping the variants that help. The end product is one self-contained multi-file code repository. Because the final product is just code, you can read it, debug it, and reuse it. (For experts: this relocates the model's expensive search out of deployment and into a one-time training phase, so on primitive-only benchmarks we chose to ship fixed Repositories-as-Policies, or RaPs.)

Unlike prior reflective optimization methods, which optimize only a single prompt, function, or delimited code region, RHO's optimizer, HELIX, searches over entire multi-file repositories at once. RHO points it at any robot-policy repository, whether Python policies, LLM agent harnesses, or skill graphs, with live robot-environment access (REaaS) isolated from the evaluator.

Watching the code teach itself

RAI O3DE: RHO optimizes deployed robotic LLM harnesses too

Here the deployment is multi-turn: a language-model agent keeps running while the robot works. Rather than write standalone code, RHO optimizes the agent's harness: its system prompt and the bodies of its tools (the agent's control interface). GPT-5.1 runs inside the harness; GPT-5.5 is the mutator. On the hard held-out split, success nearly doubles from 23.45% to 44.27% (p < 0.001, 3-run average), while using 27% fewer tool calls and 20% less wall-clock time (single representative run; the sign holds under the 3-run average).

Graph-as-Policy: RHO optimizes skill graphs too

Graph-as-Policy (GaP) runs a policy as a directed graph of human-written skills. Starting from the 20-node grocery-packing graph in the GaP codebase (LIBERO, simulated Franka, 11 instructions), we ran two RHO searches of 50 generations each with a GPT-5.6 Terra mutator. Compose-Only may add nodes and rewire the graph but must use the skills as given; Compose-and-Edit may also rewrite the skills. Both searches learned to read the instruction: grasps per single-item task fall from 4.17 to 1.04.

Why rewrite the whole codebase

On Robosuite, mutating a full multi-file repository wins in fewer generations (200 vs 250), and far outperforms rigid structured representations (behavior trees and finite-state machines).

Live simulator access helps; RHO's search gives the final push

Two GPT-6.1 Sol coding-agent sessions start from the same six-file scaffold with no task policies, the same robot API documentation, and feedback from the same 12 training trials across three task families. The only difference: one can run candidates against the live simulator (REaaS) before submitting. Each resulting repository is evaluated once on all seven Robosuite tasks over seeds 1–100 (700 trials), single-turn.

With the same GPT-6.1 Sol mutator, RHO's search closes the remaining gap: repeated sessions, the acceptance gate, and the Pareto frontier take one session's 73.00% to 99.00% (best of two searches) on the same 700 trials. The searches also trained on more trials (seeds 101–125) than the single sessions' 12. In the no-access evaluation, 34 trials ended in native simulator crashes; we replayed exactly those trials with the same policy, seeds, and evaluator and report their outcomes (13 successes).

04Sim to real

Hardware

Trained in simulation, deployed unchanged on two real robots.

We deployed the GPT-5.5 repository evolved in Robosuite without changing its policy code. Only the perception and motion APIs are swapped for embodiment-specific implementations with the same interfaces.

14/20 Franka Emika Panda, cube lifting.
11/20 Franka Emika Panda, cube stacking.
17/20 Kinova Gen3 with a Robotiq gripper, lifting a computer mouse never seen in simulation.

A new robot and a new object

On the Kinova, three things change from simulation: the search used cubes, and this is a computer mouse; the mouse moves between trials and, in this trial, during execution; and the search used a simulated Franka.

What's still hard

Recovery strategies learned in simulation cover the failures seen in simulation. On real robots, perception degrades under different cameras and lighting, so real-world success can vary even when the program logic executes correctly: the Kinova lifts an unseen mouse in 17 of 20 trials, while the nominally simpler Franka cube lift succeeds in 14 of 20.

Per-task tradeoffs remain in simulation. The GPT-5.5 repository, used for the timing and hardware results, trails CaP-Agent0 on cube restacking (54% vs 89%) and two-arm lift (53% vs 74%).
